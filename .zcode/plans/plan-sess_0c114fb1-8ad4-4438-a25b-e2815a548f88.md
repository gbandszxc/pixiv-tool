## 修复目标

让 `/api/auth/login` 真的能拉起 pywebview 登录窗,dev 和 prod 模式下都能用。

## 根因(已诊断)

`backend/auth/login_window.py:200-209` 把 `webview.start()` 塞进 daemon 二级线程,违反 pywebview 主线程硬约束。`backend.err.log` 已留铁证:
```
webview.errors.WebViewException: pywebview must be run on a main thread.
```

SPEC §3.1 的 prod 架构本来就是对的(`main.py` 主线程跑 pywebview + daemon 线程跑 uvicorn),不需要动。真正的修复点是 `login_window.py`——它独立于 dev/prod,无论哪种模式调 `/api/auth/login` 都会触发。

dev 模式 SPEC §8.1 没有 pywebview 主窗(uvicorn + Vite 双进程),所以登录只能靠"主进程外"的东西。**子进程是唯一 dev+prod 都能用的方案**。

## 方案:子进程 + 复刻 spike 主线程模式

### 文件改动

#### 1. `backend/auth/login_window.py` 重写

把 `open_login_window()` 从"线程内跑 webview"改成"作为可执行模块"。新增 `if __name__ == "__main__":` 入口,在子进程的主线程跑 pywebview(完全复刻 spike `probe.py` 的模式)。

子进程协议:
- `python -m backend.auth.login_window --result-file <path>`
- 主线程:`webview.create_window()` → `webview.start(private_mode=False, http_server=True, http_port=17729)` 阻塞
- loaded 事件(防重入)触发 → 用 `EXTRACT_AND_VERIFY_JS` 完整版提取 cookie + csrf + 验证登录态(5 次重试 + 8s/次 + callback 包装)
- 成功:cookie JSON 写到 `--result-file`,exit 0
- 用户关窗:exit 1
- 异常:错误信息写到 result file,exit 2

关键复用点(ADR 0005 复用清单):
- `EXTRACT_AND_VERIFY_JS`(4 路径 csrf + `/ajax/user/self` 登录验证)替换当前简化的 `EXTRACT_CSRF_JS`
- loaded handler 加 `state={"extracted": False}` 闭包防重入
- callback 模式 evaluate_js + threading.Event 同步包装(5 次重试)
- `http_port=17729` 固定(spike 实测可跨会话持久化 cookie)
- `cookies_to_dicts()` 和 `_morsel_to_dict()` 保留现状(已正确复用)

#### 2. `backend/api/auth.py` 的 `login()` 重写

从同步阻塞改成 spawn 子进程 + asyncio.to_thread:

```python
@router.post("/login")
async def login():
    result = await asyncio.to_thread(_spawn_login_subprocess)
    if result["status"] == "success":
        _store.save(result["cookies"])
        return {"status": "success", "message": "登录成功"}
    return {"status": result["status"], "message": result.get("error", "登录取消")}
```

`_spawn_login_subprocess()`:
- 临时文件:`tempfile.NamedTemporaryFile(suffix='.json', delete=False)`
- spawn:`subprocess.run([sys.executable, "-m", "backend.auth.login_window", "--result-file", path], timeout=300)`
- 读 result file 解析 JSON
- except `subprocess.TimeoutExpired`: return `{"status": "timeout", "error": "登录超时(5 分钟)"}`
- finally:删临时文件

关键改进:
- `await asyncio.to_thread(...)` 不阻塞 uvicorn event loop(原来同步调 300s 会卡死所有 SSE/请求)
- `sys.executable` 自动适配 dev(`.venv/Scripts/python.exe`)和 prod(打包的 Python)

#### 3. `pyproject.toml` 卡版本上界

```
win = ["pywebview>=5.0,<6.0"]
```

理由:spike 验证的是 5.4,主代码跨大版本到 6.2.1 没验证过。对齐到 spike 验证范围。然后 `uv sync --extra win --extra dev` 重锁。

### 不动的部分

- `backend/main.py`(prod 主窗架构本来对)
- `backend/storage/cookies.py` 和 `cookie_dpapi.py`(落盘归主进程管,子进程只负责提取)
- `scripts/dev.ps1`(dev 启动链不变)
- `scripts/build.py` / `pixiv-tool.spec`(子进程用 `sys.executable` 自动适配)
- `frontend/src/stores/auth.ts`(前端调用方式不变)

### 验证方式

1. `uv sync --extra win --extra dev` 装上 pywebview 5.4
2. `./scripts/dev.ps1 restart` 重启服务
3. chrome-devtools 打开 `http://localhost:9961/` → 点登录 → pywebview 窗口应弹出
4. 登录真实 pixiv 账号 → 窗口跳到 `www.pixiv.net` → 自动关闭 → 前端显示已登录 + 用户名
5. `curl http://127.0.0.1:9962/api/auth/status` 应返回 `{"is_logged_in": true, ...}`
6. 后端日志无 "pywebview must be run on a main thread" 报错

### 已知风险

- pywebview 5.4 在 Windows 11 + WebView2 最新版上是否仍能跑(spike 是 2026-07-19 测的,环境一致,应该 OK)。降级后如果 import 失败,回滚到 6.2.1 + 在 6.2.1 上重跑 spike 验证。
- 子进程模式没有跨平台测试,V1 只支持 Windows(spec §1.2 macOS/Linux 延后 V2)。子进程代码用 `sys.executable`,macOS/Linux 装了 pywebview 也能跑,但不验证。
