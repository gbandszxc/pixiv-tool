# ADR 0028：图片缓存上限可配置 + 三档分区淘汰

- 日期：2026-10-05
- 状态：已接受

## 背景

ADR 0012 把图片磁盘缓存（`<data>/cache/img/`）定死为 1GB 上限、按 mtime 从旧到新
淘汰。实际使用暴露两个问题：

1. **上限不可调**：重度浏览用户嫌 1GB 占空间，重度看图用户嫌 1GB 命中率不够，
   常量对两端都不合适。
2. **无差别 LRU 会挤掉小图**：一张原图（数 MiB 到数十 MiB）写入就把几十张缩略图
   （各几十~几百 KB）挤出新页面；而缩略图恰恰是命中率最高、重下体验最差的
   （宫格整屏裂图）。原图看一次就关，缓存价值远低于缩略图。

## 决策

**上限可配置（取代写死的 1GB，做法对齐 ADR 0023 的超时可配置）：**

- 新增设置键 `image_cache_max_mib`（整数 MiB），**默认 512**，合法区间
  256~2048；设置弹窗「图片与内容 · 图片缓存」提供预设档
  256 MiB / 512 MiB / 1 GiB / 2 GiB + 「自定义」数字输入，保存时
  bool / 非整数 / 越界一律拒绝；手改 `settings.json` 写入区间外的值在加载期
  回落默认。
- 上限在**每次图片缓存写入后实时读取**（`pixiv-img` 协议处理器从
  `AppState.settings_snapshot()` 取当前值），改小后由后续写入逐步生效，
  立即释放空间走维护页「清理」。

**三档分区淘汰（`image_proxy::trim_cache` 重写）：**

- 缓存文件按**字节数**划档：≤1 MiB 小图（缩略图 / 中等图 / 表情贴图）、
  ≤8 MiB 大图（master1200、ugoira zip 等）、其余按原图处理。
- 全局总量未超上限时**不动任何文件**——分区配额只在超限 squeeze 时生效，
  避免小图为主的缓存被硬配额白白压掉 40% 空间。
- 超限时按档施加预算（上限的 60% / 25% / 15%，小图最多、原图最低），只削
  超预算的档：档内按 mtime 从旧到新删除直至回到预算内；本次刚写入的文件
  永不被删。预算合计恰好 100%，全部档位在预算内则总量必然回到上限内。
- 单文件大于整档预算（如一张超出原图预算的巨型图）时该档只保留它自己，
  总量允许短暂越过上限，由后续写入的下一轮淘汰压回——不为此引入
  「删除刚下载文件」的复杂度。

**按字节而非 URL 形态划档的理由**：分区要约束的资源就是磁盘字节，字节数是
唯一稳定的档位信号；pximg URL 形态（`/c/250x250`、`img-master`、
`img-original`）依赖上游路径约定、对 URL 变体脆弱，且缓存目录里已有的旧文件
（内容寻址文件名之外无任何元数据）无法回溯分类。按字节划档对新旧文件零迁移
即时生效。

## 影响

设置白名单 21 → 22 键，无新增 IPC 命令、无 SQLite schema 变化、无凭据落点
变化；老配置缺键取默认 512（比旧的 1GB 更保守，不想被降的调回 1024 即可），
不需要迁移脚本。维护页的「图片缓存」总大小、清理与复制路径行为不变；
`maintenance_info` 仍回报目录实际字节。ADR 0012 中「上限 1GB 按 mtime 淘汰」
的细节由本 ADR 取代，其余决策不变。日志纪律不变：清理仍只记一条 info
（删除计数按档分列、剩余/上限字节数），不打印 URL 与用户路径以外的内容。
