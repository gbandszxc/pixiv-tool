# ADR 0036：翻译运行层窗口防护与任务续跑

- 状态：已接受（细化 [ADR 0035](0035-whole-novel-agent-translation.md) 的运行层行为；不推翻其决策）
- 日期：2026-10-25
- 关联 ADR：[ADR 0033](0033-translation-dynamic-output-cap-and-default-thinking.md)、[ADR 0034](0034-rig-agent-kernel-and-rust-toolchain.md)、[ADR 0035](0035-whole-novel-agent-translation.md)
- 规格：[SPEC](../SPEC.md) §4.3

## 背景

真实故障（2026-10-25，一篇 1 页 6 块的短篇、两个模型先后失败）暴露了运行层的两个缺陷：

1. **单轮并行读块拉爆窗口**。协调者模型一次并行调用全部 `read_chunk`（6 块 × 块内容 + 邻接窗口 ≈ 32k tokens），一次性进入下一轮请求的 prompt。上下文压缩器只覆盖 rig-agent 传入的 `history`（每轮最后一条消息作为 prompt 单独传入），对 prompt 内的工具结果无能为力；压缩器看到的历史只有约 900 tokens，报「没有可压缩的历史」，随后窗口检查直接以 `input_too_large` 终止任务。
2. **模型提前收工任务即停**。另一模型在第 5 轮输出纯文本（不再调用工具），本轮运行正常结束；服务层只执行一次 `runtime::run`，完成校验不通过就直接转 `needs_attention`（incomplete），没有任何续跑机制，任务停在准备阶段直到用户手动取消。
3. **续跑后空转**（第一版修复后的复测）。模型读到 2 个块后再次输出纯文本收工；续跑重放主提示，模型连续三轮只调用 `job_status`、输出约 600～800 tokens 的汇报文本后结束，产物零增长，最终仍以 `incomplete_scan` 失败。说明「重放主提示 + 让模型自己读状态」不足以改变行为模式。

提示词约束（如「单轮最多读 2 块」）不能作为防线——模型行为不可控，运行层必须自行设防。

## 决策

### 1. 单轮工具结果预算（第一道防线）

- 运行层在 `on_dispatch` 钩子按「工具名 + 参数」预估每个工具调用的结果 token（`ToolResultEstimator`，由翻译服务提供：`read_chunk` 按块字符数 + 邻接窗口 + 结构开销估算，其余工具返回 0 不参与）。
- 单轮（两次模型调用之间）累计预估量超过预算时，拒绝执行剩余调用（`DispatchAction::skip`），模型收到跳过原因并在下一轮分批读取；已执行的结果不回滚。
- 预算公式：`可用输入 − 固定开销（系统提示 + 工具 schema）− 历史保留`，下限 1024。历史保留取「最近消息上限与摘要上限之和」（`min(recent_tokens, 8192) + summary_tokens`），与压缩器实际保留量一致；上限 8192 防止把整个最近窗口都从预算里扣掉。公式保证「预算内的结果 + 固定开销 + 压缩到保留区内的历史」装得下可用输入；下限防止极小窗口把预算压到 0 后模型完全读不到任何块。
- 单块内容超过整个预算时（多为窗口配置不足），任务以 `no_progress` / 轮次上限收敛到 `needs_attention`，跳过提示中说明需要调大窗口或调小块大小。

### 2. 紧急截断（最后防线）

- 常规压缩救不回来时（无可压缩历史，或压缩后仍超窗），对历史中较早的**成功**工具结果正文按「头尾保留 + 中段省略标注」截短；从最旧到最新，一轮不达标按半深迭代收紧单条上限（最低 64 tokens）。错误结果与消息结构（工具调用与结果的配对）不动。
- 截断后的投影写回压缩缓存，后续轮次复用；截断标注提示模型「如需完整内容请重新读取」。被截断的结构化 JSON 不再可解析，模型（与幂等脚本）应重新读取——这是有损的最后防线，优先级低于预算拦截与正常压缩。

### 3. 任务级续跑循环

- 服务层的 `drive()` 从「单次运行」改为续跑循环：一轮运行**正常结束**但完成校验未通过、且未被取消 / 暂停 / 等待确认时，带着该轮带回的压缩后历史投影（`RunOutcome::history`）与运行层生成的续跑指令重新拉起运行。
- 连续无进展（产物计数无增长，按磁盘上的草稿 / 审查 / 冻结 / 发布产物衡量）达到 2 次续跑才转 `needs_attention`（incomplete；消息附模型最后一轮说明）；任何产物增长都重置计数。任务级推进不再受单轮 `max_turns` 限制；总量仍受调用预算与模型尝试上限约束。
- 运行失败（`Err`）不续跑，按既有恢复分类处理；进度快照直接数产物而非 manifest 计数，避免计数更新时机影响判断。

### 3.1 续跑指令（修复空转）

- 续跑不再重放主提示。运行层按磁盘产物计算待办（与 `job_status` 共用 `pending_state`），生成一条直接给出下一步动作的 user 消息：当前卡住的阶段、待办块 ID 清单、该阶段应调用的工具及其参数要求。
- 指令明确声明「只输出计划、总结或扫描 / 译文正文都不算完成，本轮回复必须包含工具调用」，并要求不要重复调用 `job_status`（清单已由运行层给出）。
- `submit_scan` 的参数 schema 补全为显式的 `terms[]` 字段（`source_term` / `locked_translation` 必填），减少模型因无法构造参数而把结果写进普通回复。工具描述同时说明「扫描结果必须通过工具写入」。
- 复测仍出现「读完两块后只输出文本」：续跑轮 `tool_calls=0` 且回复数百字符，说明模型把扫描结论写进了普通回复。续跑指令因此升级——`run_done` 之后若上一轮完全没有工具调用，追加一条更强要求（本次回复只允许是工具调用，不得复述扫描结果），并在扫描分支内嵌 `submit_scan` 的最小 JSON 示例。
- 连续无工具调用的轮次单独计数（`empty_runs`），达到 2 轮即收敛为 `needs_attention`（此时错误码为 `model_declined`）——这类空转每轮都在烧整段上下文，收敛要快。
- `run_done` 日志增加 `final_chars` 与 `final`（最终回答前 300 字符），用于确认模型究竟把什么写进了回复。
- 实际根因由 `final` 确认：模型是在做**内容审核拒绝**（作品含未成年角色的露骨描写），并非参数构造失败。因此零工具调用收敛时不再报笼统的 `incomplete_*`，而是 `model_declined`，消息直接引用模型最后一轮说明；应用不尝试绕过模型的内容策略，用户可据此判断是否需要更换模型或放弃该作品。

### 3.2 可重试失败的任务级重试

- 复测时再次暴露：模型服务返回 `429`（上游容量不足）时，`RunError::Provider { class: Retryable }` 直接把任务推入 `needs_attention`，尽管存在 `RetryPolicy`，它此前只用于子任务重试。
- `drive()` 现在对可重试的模型请求失败按设置的重试次数（`translation_agent_retry_limit`）与退避（`backoff_base_ms` / `backoff_max_seconds`）重跑整轮；退避等待可被暂停 / 取消中断。用尽后才按原路径转 `needs_attention`。
- 失败轮没有可带回的历史，保留上一轮 `carried`，并追加同一份续跑指令（原因改为「上一轮模型请求被服务端暂时拒绝」），避免重试轮从零猜测进度。每次重试记 `run_retry` 日志（尝试序号与错误码）。
- 重试与「无进展续跑」分开计数：限流重试不消耗 `MAX_IDLE_CONTINUATIONS`，产物增长仍会重置空转计数。

### 3.3 派发失败的块级隔离与预算扩容

- 真实任务（5 块、约 9,400 字）在 96 次调用内耗尽预算，日志显示「翻译 → 审查 → 重译 → 再审」反复：审查子任务先因 `output_truncated`、随后因 `429` 与 `unknown_outcome` 失败，`dispatch_review` 把这些失败聚合成整批 `fatal`，协调者据此结束本轮；续跑又把整批未审块重新派发，每块 2～4 次模型调用，预算被快速打满。
- 修正：只有全局性错误（`permanent` / `budget_exhausted`）才把整批标 `fatal`；单块 `unknown_outcome` 只标记该块，其余块照常返回。结果未知且按设置不重放的块记入 `unknown_blocked`，后续派发直接短路（不再发请求），用户手动恢复任务时清空。
- 自动调用预算从 `32 + 16 × 初始分块数` 上调到 `64 + 32 × 初始分块数`：扫描、翻译、审查各是一次独立子 Agent 会话，再加主 Agent 调度、压缩摘要与失败重派，单块真实调用量远高于 16。设置项 `translation_call_budget` 仍可显式覆盖（0 = 自动）。
- 块列表由快照的 `chunk_ids`（分块计划顺序）提供：细分后块 ID 不连续（如计划为 c0001/c0002/c0005/c0006/c0004），前端按序号拼 ID 会显示已废弃块并漏掉新块，预览页因此与顶部计数矛盾。前端在进度计数变化时丢弃预览缓存并重取，避免早期「未译」一直滞留。
- 审查截断的根因在上游：审查子任务按输入分档申请 65k 输出上限，但网关在约 8～10k 处封顶，模型写完 9.4k 的分析后 `submit_review` 还没发出去就 `finish_reason=Length`。审查改为固定 `reasoning_effort=low`，契约要求「读完一块立即 `submit_review`，不写分析正文，detail ≤ 120 字、issues ≤ 5 条」，把输出压回几百 token。

### 4. 资源文档与角色边界

- 协调者角色与 `smart-translator` 技能补充「单轮并行 `read_chunk` 不超过 2 个、收到预算跳过提示后分批读取」的指引。指引只用于降低无效轮次，不是防线。

## 后果

- 窗口内不再可能被一轮并行工具调用击穿；`input_too_large` 只在「单块内容本身超过整个可用输入」时出现，且错误语义明确指向配置问题。
- 模型中途输出文本不再终结任务；长任务跨多次运行推进，日志与事件按 `run_continue` / `continuation_stopped` 区分。续跑指令给出明确动作后，模型不再靠自行读状态猜测进度，也不会把扫描结果留在普通回复里。
- 每次续跑的用量、压缩与工具轨迹都独立记入会话 journal；`run_done.final_chars` 与 `run_continue.idle` 一起可还原「空转 → 续跑 → 收敛」的过程。
- e2e 覆盖：批量读块被预算节流后任务仍完成（跳过提示回传模型）；模型提前收工后自动续跑到完成，并断言续跑轮收到「必须包含工具调用」的指令；主 Agent 首次请求返回 429 后退避重试并最终完成。压缩有损性的边界（截断破坏 JSON 结构后由幂等工具重读自愈）由同一用例覆盖。
